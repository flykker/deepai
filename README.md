# deepai-agent

AI-агент на **python + langgraph + deepagents** с **background tasks как в Claude Code**.

Долгие команды (dev-server, build, watcher, тесты) запускаются в фоне, агент не
блокируется, получает task id и файл с выводом, а когда задача завершается —
в разговор автоматически вставляется уведомление, которое «будит» модель.
Опроса в цикле не нужно.

## Соответствие Claude Code

| Claude Code | Здесь | Где |
|---|---|---|
| `Bash(run_in_background=true)` | `start_background_task(command, description, timeout_ms?)` | `agent/background/middleware.py` |
| `BashOutput` / чтение output-файла | `get_task_output(task_id, filter?)` — только новый вывод с прошлого чтения + статус | там же |
| `KillShell` / `TaskStop` | `kill_task(task_id)` — SIGTERM по всей группе процессов, затем SIGKILL | там же |
| `/tasks`, `/bashes` | `list_tasks(status?)` (для модели) и `/tasks` в CLI (для человека) | middleware + `agent/main.py` |
| `<task-notification>` в конце хода | `render_notifications()` + цикл в `AgentHarness` | `agent/background/notifications.py`, `agent/harness.py` |
| `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` | `DEEPAI_DISABLE_BACKGROUND_TASKS=1` — инструменты исчезают из схемы | `agent/background/middleware.py` |
| kill фоновых задач при выходе из сессии | `AgentHarness.close()` → `BackgroundTaskManager.shutdown()` | `agent/background/manager.py` |
| `Bash` (foreground, таймаут) | встроенный `execute` от deepagents (`LocalShellBackend`, таймаут 120 c) | `agent/graph.py` |

## Архитектура

```
agent/
├── graph.py                  # сборка агента: create_deep_agent + LocalShellBackend + middleware
├── harness.py                # ходы диалога, стриминг вывода, ВНЕДРЕНИЕ уведомлений
├── main.py                   # CLI: репла, /tasks, /help, /exit
└── background/
    ├── manager.py            # фоновые процессы: spawn, вывод, kill, очередь событий, tasks.json
    ├── middleware.py          # 4 инструмента + state `background_tasks` + промпт
    └── notifications.py       # рендер <task-notification>
evals/                        # eval-сьют: сценарии, независимые чеки, отчёты
├── recorder.py                # events.jsonl через LangChain-callbacks
├── checks.py                  # pytest/сервер/утечки — проверяет раннер, не модель
├── runner.py + report.py      # песочница, вердикт, метрики, --baseline, --trend
└── scenarios/                 # webapp, parallel, devserver
tests/                        # 76 тестов, без API-ключей (фейковая модель)
```

Ключевые решения:

1. **`BackgroundTaskManager`** — один на сессию, живёт вне графа. Запускает
   `subprocess.Popen(shell=True, start_new_session=True)`, склеивает stdout/stderr
   в `<tmp>/deepai-bg-tasks/<session>/<task_id>.output`, поток-наблюдатель ждёт
   завершения и кладёт задачу в очередь уведомлений. `read()` возвращает только
   байты, появившиеся с прошлого чтения (офсет хранится в памяти).
2. **Снимок задачи (`BackgroundTask`)** — чистый JSON: он живёт в состоянии
   LangGraph под ключом `background_tasks` (свой reducer, merge по `task_id`),
   поэтому переживает checkpointer. Хэндлы процессов и офсеты из состояния не
   выходят.
3. **Уведомления внедряет харнесс, а не модель.** В Claude Code харнесс после
   хода вставляет `Background command "..." completed (exit code 0)`. Здесь то же
   самое: `AgentHarness.run_turn()` → дождаться очереди → новое сообщение
   пользователя с `<task-notification>` → ещё один вызов графа. Уведомления
   доставляются и **до** нового сообщения пользователя (задача могла завершиться,
   пока сессия простаиваила), и **после** каждого хода, а если ход уже кончился —
   их доставляет фоновый нотификатор `AgentHarness._notify_loop`: он ждёт
   завершения задачи по Condition'у менеджера и будит модель, не дожидаясь
   следующего сообщения. Одновременно идёт только один запуск графа — их
   сериализует `RLock` харнесса.
4. **Статусы читаются заново.** `list_tasks`/`get_task_output` ходят в менеджер, а
   не в старое состояние, поэтому ответы в контексте не устаревают.
5. **Фон или foreground — решает модель, параллельность — тоже.** Порог «больше ~10
   секунд → в фон» и правило «независимые долгие команды запускай несколькими
   `start_background_task`-вызовами **в одном ответе**» записаны в описании
   инструмента и в системном промпте (`agent/background/middleware.py`).
   LangGraph исполняет несколько tool-вызовов из одного сообщения в пуле
   потоков, а сами процессы независимы — поэтому N вызовов дают N
   одновременно бегущих процессов (тест
   `test_parallel_tool_calls_start_concurrent_tasks`).
   Правило генерализовано в `BATCHING_PROMPT` (`agent/graph.py`): батчатся
   **любые** независимые вызовы шага — несколько `write_file`, чтение вывода
   после уведомления вместе со следующим действием. На eval это вместе с
   дедупликацией уведомлений (п. 10) срезало webapp с 28 ходов до 14 при
   бюджете 16.
6. **Вызовы модели ограничены по времени.** Клиент по умолчанию ждёт
   «залипшего» прокси до 10 минут — это выглядит как зависшую сессию. Для
   OpenAI-совместимых провайдеров `resolve_model_spec()` проставляет
   `AGENT_MODEL_TIMEOUT` (30 с) и `AGENT_MODEL_MAX_RETRIES` (4); при сбое
   доставки уведомления возвращаются в очередь и уходят при следующем ходе.
   Значения подобраны по данным eval: здоровый ответ даёт первый токен за
   2–4 с (легитимный максимум — 16 с), «мёртвая» попытка обрывается ровно по
   таймауту, а худший случай ≈ `(ретраи+1) × (таймаут + ~3.5 с)`. История:
   60 с × 3 → 125–190 с тишины; 25 с × 3 → прокси убивал SSL-handshake и ход
   падал; 40 с × 2 → один ~2-минутный outage прокси оборвал ход; сейчас
   30 с × 5 попыток переживают outage до ~2 минут.
7. **Корень песочницы — `/`, а не `pwd`.** Файловые инструменты deepagents
   резолвят абсолютный путь от корня (`cwd / path.lstrip("/")`), схема
   `write_file` при этом требует «абсолютный путь», а shell печатает хост-путь
   — и модель устраивала запись файлов в `workspace/public/.../workspace/app.py`
   (прогон eval это поймал как FAIL: «нет app.py»). Теперь в системном промпте
   всегда есть секция `SANDBOX_PATHS_PROMPT` (`agent/graph.py`): «`/` — корень
   проекта, `pwd` обрезается до workspace, шелл-командам хост-пути всё равно
   можно».
8. **Ждать — значит закончить ход.** Прогон eval показал модель, которая
   дважды опросила `get_task_output` и ушла в `execute("sleep 25")`, вместо
   того чтобы завершиться: каждый такой шаг — потерянные ходы, токены и
   секунды. Теперь описания инструмента и системный промпт прямо это
   запрещают: сообщил, что запустил, — закончил ход, а `<task-notification>`
   придёт сам, без нового сообщения пользователя.
9. **Обрыв связи с моделью — повод продолжить ход, а не бросить его.**
   Прокси роняет соединение посреди хода: eval ловил `OpenAIConnectionError`
   на 372-й секунде, когда все задачи уже были сделаны, — ход умирал вместе
   со своим прогоном. Клиентские ретраи тут не помогают (запрос уже ушёл и
   частично выполнен), поэтому повтор живёт в харнессе: `_invoke` ловит
   временные ошибки (`ConnectionError`/`TimeoutError` и одноимённые классы
   openai, `RateLimit*`, `InternalServerError`), ждёт `2×попытка` секунд и
   продолжает ход с чекпоинта LangGraph — `invoke(None)`. Ввод повторно не
   отправляется (иначе сообщение пользователя легло бы в состояние дважды),
   выполненные суперстепы не переигрываются — resume стартует с упавшего
   шага. Дефолт `model_turn_retries=2`, непостоянные ошибки всплывают сразу
   (`tests/test_harness.py`, четыре теста на эту ветку).
10. **Уведомление — только если это новость.** Модель может сама прочитать
   вывод задачи раньше, чем харнесс доставит уведомление о её завершении
   (так и случилось на eval: прочитанные bash-1/bash-2 пришли уведомлениями
   *после* финального ответа и запустили ~10-ходовую «ревизию» собственного
   summary, сжегшую лимит прогона). Менеджер запоминает статус, наблюдавшийся
   при последнем чтении задачи (`last_read_status`), и `take_notifications`
   отбрасывает уже увиденные терминальные статусы — модель всегда узнаёт о
   завершении ровно один раз, а промпт поясняет: пришедшее уведомление всегда
   новость, читать его заново и перепроверять прочитанное не нужно.

## Запуск

```bash
python -m venv .venv && .venv/bin/pip install -e ".[dev]"

export ANTHROPIC_API_KEY=...        # или OPENAI_API_KEY / GOOGLE_API_KEY
export AGENT_MODEL=anthropic:claude-sonnet-4-6   # или openai:gpt-5.1, ...

.venv/bin/python -m agent.main --root /path/to/project
```

В `.env` этого проекта зафиксирована `AGENT_MODEL=openai:qwen3.8-flash` — она
прошла все три eval-сценария подряд (`--trend`); у `deepseek-v4.1-flash`
вечерняя серия рвалась на ошибках прокси. Модель меняется одной строкой в
`.env` или флагом `--model` у eval-CLI.

Команды в репле: `/tasks [status]`, `/help`, `/exit` (при выходе фоновые
процессы убиваются). `--prompt "..."` — один ход и выход, `--quiet` — без
стриминга, `--thread-id` — продолжить конкретный диалог.

Пример хода:

```
> собери проект
  ● start_background_task({"command": "npm run build", "description": "build project"})
  ⎿ [start_background_task] Command running in background with ID: bash-1. ...
Сборка запущена в фоне.

● Background command "build project" finished: completed (exit code 0)
```

## Тесты

```bash
.venv/bin/python -m pytest
```

Тесты не ходят в сеть: модель подменяется на `FakeToolModel`
(`tests/conftest.py`), поэтому проверяются реальные пути — запуск/чтение/kill
фоновых процессов, инструменты в графе, доставка уведомлений в нужной позиции
разговора, CLI, а также сам eval-сьют (`tests/test_evals.py`). Фейковая
модель умеет сценарий сбоя (`_Replay` в `conftest.py` бросает заложенную
ошибку и продолжает сценарий) — так проверяется повтор хода при обрыве связи.

Сеть проверяется отдельным демо (нужен заполненный `.env`):

```bash
.venv/bin/python -u demo_parallel.py   # 3 фоновые задачи одним ответом + уведомления
```

## Eval-сьют: как измеряем и улучшаем агента

`evals/` — прогон сценариев на реальной модели с независимой проверкой
результата и отчётом, по которому видно, что чинить.

```bash
.venv/bin/python -m evals --list              # какие есть сценарии
.venv/bin/python -m evals parallel            # быстрый: 3 фоновые задачи в батче
.venv/bin/python -m evals webapp              # «напиши приложение, тесты, прогони»
.venv/bin/python -m evals --all               # всё подряд
.venv/bin/python -m evals webapp --baseline runs/<старый_прогон>   # дельта метрик
.venv/bin/python -m evals --trend             # таблица метрик по всем прогонам истории
```

Каждый прогон — свежая песочница и самодостаточный каталог артефактов:

```
runs/20260926-120000_webapp/
├── events.jsonl      # таймлайн: llm_start/first_token/llm_end/tool_start/…
├── transcript.json   # вся переписка (что модель ответила, какие вызовы сделала)
├── report.md         # вердикт, метрики, проверки, артефакты, слабые места
├── report.json       # те же цифры для --baseline-сравнения
├── workspace/        # сюда агент пишет код (app.py, test_app.py, …)
└── tasks/            # вывод фоновых задач (bash-*.output)
```

Проверки независимы от агента (`evals/checks.py`): раннер **сам** запускает
написанные тесты, **сам** поднимает `app.py` и стучится в `/hello`, смотрит,
не остались ли фоновые задачи висеть. Утверждения модели в расчёт не берутся.

Метрики, на которые смотрим при улучшениях: число LLM-ходов, tool-вызовы по
типам, `start_background_task`, поллинги `get_task_output`, батчи из ≥2
вызовов, столлы модели (ожидание первого токена >10 с), ошибки, токены, время.
В `--quiet` harness вызывает граф через `invoke` (без стриминга), токены не
приходят — тогда ожидание считается по полной длительности вызова
(`report.wait_ms`), поэтому столл виден и там.
`qwen3.8-flash` через прокси не отдаёт `usage` — в таких прогонах
`tokens_in/out` равны 0 (это видно в `--trend`), сравнивать по токенам можно
только прогоны одной модели.
По ним же `report.md` сам подсказывает слабые места («поллинг вместо
ожидания уведомлений», «задачи не батчатся», «столл прокси»).

У каждого сценария есть **бюджеты эффективности** (`max_llm_calls`,
`max_polls`, `max_duration_s`): правильный, но вдвое более дорогой прогон
больше не проходит молча — превышение по ходам и поллингу валит вердикт
(«бюджет: ходов LLM ≤ 16 — факт 18»), превышение по времени лишь
предупреждает: секунды зависят от погоды прокси, а ходы — от агента.
Текущие лимиты выставлены по истории прогонов (`--trend`): parallel 7/6/150,
devserver 9/3/180, webapp 16/5/420.

Цикл улучшений: `baseline → правка промпта/описания инструмента → прогон →
--baseline дельта → оставляем или откатываем`. Сценарии лежат в
`evals/scenarios/` (сейчас `webapp`, `parallel`, `devserver` и `debug`),
новые добавляются файлом + записью в реестр `evals/scenarios/__init__.py`.
`devserver` проверяет жизненный цикл долгой задачи: поднять сервер, получить
200, убить `kill_task`, убедиться, что порт слушать перестал.
`debug` — единственный сценарий не «сгенерировать», а «починить»: хук
`Scenario.setup` сажает в песочницу готовое `app.py` с двумя спрятанными
багами и *корректный* `test_app.py`, а чек `file_content_is` пинит тесты
байт-в-байт — починка тестами вместо кода это FAIL.

`--trend` читает `runs/*/report.json` и печатает одну таблицу по всей
истории: ходы, tool-вызовы, фон, поллинги, столлы, секунды, токены — по ней
видно, улучшается ли агент от цикла к циклу.

## Ограничения и следующие шаги

- Персистентность менеджера: записи о задачах пишутся в `tasks.json` рядом с
  выводом (`--root`-CLI держит стабильную сессию на проект, переопределяется
  `DEEPAI_SESSION_ID`). После рестарта история остаётся: завершённые задачи
  читаются целиком (файл вывода с начала), а погибшие вместе со старым
  процессом возвращаются со статусом `interrupted`. Процесс заново не
  переподключается — pid прошлой сессии ничего не значит.
- Если доставка уведомления упала (модель недоступна), оно возвращается в
  очередь и уходит при следующей попытке — потеряться не может.
- «Фоновые агенты» (запуск целых субагентов в фоне) — отдельная история: в
  deepagents для этого есть `AsyncSubAgentMiddleware` (нужен LangGraph Platform /
  Agent Protocol сервер). Сюда он не встраивался, но ложится на тот же паттерн:
  `start_* → task_id → check → уведомление`.
